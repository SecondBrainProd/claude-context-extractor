## Принцип маршрутизации

База контекста **НЕ франшиза-центрична**. Большинство процессов — самостоятельные функциональные процессы, и каждый идёт в ОДНУ профильную папку. Папка `01_Франшиза` — такая же, как остальные; используй её только когда у процесса есть **самостоятельный** франшизный контекст (контрактные обязательства сети перед партнёрами, правила для партнёрских точек как отдельная сущность), а не каждый раз, когда франшиза просто упоминается фоном.

### Атомарность — ГЛАВНЫЙ принцип

**Каждая самостоятельная as-is ситуация = ОТДЕЛЬНАЯ атомарная заметка.** Если в транскрипте несколько разных снимков текущего состояния — даже про ТЕСНО СВЯЗАННЫЕ сущности в одной области — это РАЗНЫЕ заметки, связанные ссылками, а НЕ один общий файл-«простыня». Цель — цеттелькастен из атомарных as-is, а не большие сводные документы.

**Соблазн слить связанные сущности в один файл — главная ошибка этого агента.** При малейшем сомнении «слить или разнести» — РАЗНОСИ и связывай ссылками, не объединяй.

Пример (запомни буквально): «Ведение карточки отправителя», «Справочник типов отправителей», «Привязка прайсов к отправителю», «Привязка предзаказов к отправителю» — это ЧЕТЫРЕ разных as-is про одну сущность «Отправитель» → ЧЕТЫРЕ атомарные заметки, перелинкованные между собой. НЕ один файл «Управление отправителями». То, что у них общая сущность или область — НЕ повод сливать.

**Тест атомарности:** «Является ли это самостоятельным снимком текущего состояния, на который осмысленно сослаться из других заметок?» Если да — отдельная заметка.

**Защита от пере-дробления:** заметка должна быть самодостаточной (одна осмысленная as-is ситуация), а не обрывком в одно предложение. Не дроби единую связную ситуацию на фрагменты. Атомарно — значит «одна цельная as-is», а не «одна фраза».

---

**Поведение по умолчанию: одна самостоятельная as-is → одна атомарная заметка. Объединение нескольких as-is в один файл — почти всегда ошибка.**

1. **Каждая самостоятельная as-is → своя заметка в наиболее профильной папке.** Это дефолт.

2. **Разные as-is → разные заметки**, даже если относятся к одной папке, одной области и одной сущности. Объединяй в один файл ТОЛЬКО буквальный под-шаг, который не имеет никакого смысла отдельно от родителя.
   - *Разные as-is (одна сущность «Отправитель»):* «Ведение карточки» И «Справочник типов» И «Привязка прайсов» → 3 атомарные заметки со ссылками. НЕ один файл.
   - *Разные as-is (одна папка):* «Процесс розничных продаж» И «Модель компенсаций в рознице» → 2 файла в `02_Розничные продажи`.
   - *Буквальный под-шаг (внутри):* отдельный экран ввода внутри одной процедуры, не осмысленный сам по себе → внутри родителя.

3. **Процесс относится к нескольким областям → выбери ОДНУ, где он раскрыт полнее.** Не дублируй один файл в несколько папок. Связь с другими областями выражай через `Зависит от:` / `Влияет на:` со ссылками `[[...]]`, а не копией файла. Среди этих областей **не обязана** быть франшиза.

4. **Парные файлы — только при самостоятельном франшизном контексте.** Два файла (один в `01_Франшиза`, второй в функциональной папке) создавай ТОЛЬКО если франшизный аспект процесса несёт отдельный смысл, который стоит описать самостоятельно. Если франшиза — просто фон или упоминание, это НЕ повод для пары: делай один файл в профильной папке.

   **Если сомневаешься, нужна ли пара — НЕ создавай её.** Делай один файл в наиболее профильной папке. Не выноси решение о маршрутизации в пакет уточняющих вопросов — выбор папки и файлов детерминирован этими правилами и показывается пользователю в плане (Plan Mode). Если франшизный аспект потенциально мог бы заслуживать отдельного файла, отметь это в плане одной строкой как пункт на подтверждение (например: «франшизный аспект описан внутри основного файла; отдельный файл (Франшиза) не создаю — подтвердите, если нужен»), но НЕ блокируй вопросом.

   Когда пара действительно оправдана, давай файлам суффиксы-уточнители, чтобы вики-ссылки не конфликтовали:
   - `01_Франшиза`: `# Заголовок (Франшиза)` → файл `Заголовок (Франшиза).md`
   - функциональная: `# Заголовок (ИТ)` → файл `Заголовок (ИТ).md` (суффикс = имя папки без номера)

## Как выбрать сценарий

Перед маршрутизацией выполни поиск по рабочему пространству:

1. Используй `Glob` по функциональным папкам (`02_Розничные продажи/`, `08_ИТ/` и т.д.) для поиска `.md`-файлов, которые покрывают данный процесс.
2. Если найден файл, описывающий тот же процесс или систему — применяй **Сценарий А** (обновление).
3. Если ни один существующий файл не покрывает процесс — применяй **Сценарий Б** (создание нового).

> Поиск проводится только в функциональных папках. Папка `_review/` при поиске не учитывается.

> **ИНВАРИАНТ ПОКРЫТИЯ (важнее выбора сценария).** Выбор А/Б НИКОГДА не уменьшает покрытие. Каждая самостоятельная as-is из транскрипта получает результат: новую заметку (Б) ИЛИ обновление (А). «Тема уже есть в базе» и «база собрана из более свежего источника, чем транскрипт» — НЕ основание пропустить ситуацию или не создать заметку; такая as-is идёт в **обновление (А)**. Пропуск (без новой заметки и без обновления) допустим ТОЛЬКО после фактического чтения КОНКРЕТНОЙ существующей заметки, целиком содержащей эту as-is — тогда ставится связь, и ситуация считается покрытой. Свежесть базы сама по себе пропуском не является. Подробности — Правило 7 агента `context-extractor`.

---

## Сценарий А: Обновление существующего файла

Применяется, когда транскрипт дополняет или уточняет информацию, уже зафиксированную в существующем файле контекста.

**Правила:**
- **Уточнение/детализация:** если новый транскрипт добавляет детали или исправляет существующее — редактируй текст по месту, встраивая новые факты в соответствующие разделы. Не добавляй отдельный блок в конец файла.
- **Противоречие:** если новый транскрипт противоречит уже зафиксированному контексту — не разрешай противоречие самостоятельно; добавь его в пакет вопросов пользователю вместо слияния.
- Старая важная информация не удаляется, если только в новом транскрипте она явно не отменена — причём «отмена» засчитывается ТОЛЬКО когда твой транскрипт НЕ СТАРШЕ `source` этого факта. Отмена более свежего записанного факта более старым транскриптом — это противоречие: идёт в пакет вопросов, а не в молчаливое удаление (см. правило асимметрии в Правиле 7 агента).
- **Синтез, а не откат.** Обновление ОБЪЕДИНЯЕТ старое и новое: по каждому факту остаётся более полная/точная формулировка, дельта транскрипта вплетается. Существующие факты заметки НЕ выкидываются за то, что их нет в текущем транскрипте (у заметки своя история источников в `source:`). Пропустить апдейт («нет дельты») можно ТОЛЬКО прочитав КОНКРЕТНУЮ заметку и убедившись, что она уже содержит эту as-is целиком — НЕ по одному взгляду на `source:` и НЕ потому что «база свежее»; ситуация при этом считается ПОКРЫТОЙ (ставь связь), а не выпавшей. Возраст сам по себе не делает источник правильнее; решает наличие нового, а не «кто свежее». При конфликте формулировок, когда твой транскрипт старше `source` заметки, — НЕ переписывай, вынеси в вопросы (откат под видом уточнения недопустим).
- **Приведение к текущим правилам (важно).** Обновляемая заметка приводится к АКТУАЛЬНЫМ правилам оформления ЦЕЛИКОМ, а не только в добавляемых кусках. **Правила агента и словарь важнее стиля существующей базы.** Конкретно при обновлении: снимай висячие ссылки на сущности (`[[Отправитель]]`, `[[1С]]` → обычный текст, по Правилу 3 агента); заменяй неканонические имена на канонические из `glossary.md`, ДАЖЕ если они стоят внутри `[[ссылок]]` (`[[Отдел маркетинга]]` → `Департамент маркетинга`, по Правилу 4). НЕ сохраняй устаревший стиль базы «ради консистентности» или «ради совпадения ссылок» — обновление и есть момент привести заметку в соответствие. Ссылки на ДРУГИЕ существующие as-is заметки при этом сохраняются (они валидны).

### ФОРМАТ ВЫВОДА ДЛЯ ОБНОВЛЕНИЯ

Пиши ПОЛНУЮ обновлённую версию заметки ПЛОСКО в `_review/<Заголовок>.md` (имя файла = заголовок оригинала; целевая папка оригинала указывается в `folder:`) — целиком переписанную по текущим правилам, с вплетёнными новыми фактами. **Включи тот же frontmatter, что и у новых заметок** (`folder:`, `source_type:`, `source:`, `created:`, `modified:`). Правила при обновлении: `source` НЕ затирается, а дополняется — новый источник добавляется к существующим (YAML-список), история источников сохраняется; `created` НЕ меняется (дата первого создания); `modified` обновляется на дату текущего прогона. Если в заметке остался старый `source_date` — удали его (поле упразднено, дата источника видна из имени в `source`). Оригинал в функциональной папке НЕ трогай — он будет заменён на этапе раскладки (`/context-extractor:apply-review` положит обновлённую версию поверх оригинала) либо пользователь перенесёт вручную. НЕ используй точечный формат «замените блок под заголовком» — клади готовую полную заметку.

**Пометь изменения маркером для проверки — ТОЛЬКО в обновлениях (Сценарий А).** Новый или изменённый по СОДЕРЖАНИЮ текст в обновлённой заметке оборачивай в `<mark>...</mark>` (HTML-маркер). **НЕ используй `==...==`** — он ломает Dataview; маркер только `<mark>`. Помечай новые факты и поправленные формулировки. Служебную чистку оформления (снятые висячие ссылки, канонизацию имён) маркером НЕ помечай — она идёт в строку «Что изменено». Это маркеры ревью: пользователь снимает их после проверки. Если в исходной заметке остались старые маркеры (`<mark>...</mark>` или `==...==`) от прошлого обновления — сними их (уже проверены) и помечай только изменения ТЕКУЩЕГО прохода. **В НОВЫХ заметках (Сценарий Б) маркеров `<mark>` НЕ ставь вообще** — там весь текст новый, помечать нечего; маркер появляется исключительно в обновлениях существующих заметок.

В плане по каждому обновляемому файлу дай строку:

```
Что изменено: [новые факты + что приведено к правилам (снятые висячие entity-ссылки, заменённые на канонические имена) — для проверки пользователем]
```

## Сценарий Б: Создание нового файла

Применяется, когда транскрипт описывает процесс или систему, которые ещё не зафиксированы ни в одном из существующих файлов контекста.

**Правила:**
- Форму, структуру и глубину заметки задаёт ФОРМАТ ВЫВОДА ниже (шаблон + эталон глубины), а НЕ существующие заметки базы. НЕ равняй детализацию на соседние заметки: лаконичная база ужимает новые заметки до куцых. Базу используешь только для дедупа, связей и противоречий — не как образец формы.
- Новый файл создаётся по формату ниже.
- Файл сохраняется ПЛОСКО в `_review/<Заголовок>.md` — БЕЗ подпапок. Целевая папка задаётся ТОЛЬКО полем `folder:` во frontmatter, а не структурой каталогов `_review/`. `_review/` — это просто плоская очередь заметок на проверку. Имя файла — точная копия заголовка документа (`# ...`) на кириллице, с сохранением регистра. Пример: заголовок `# ИТ-поддержка партнёрских точек` → файл `_review/ИТ-поддержка партнёрских точек.md` со строкой `folder: 08_ИТ` в шапке. **Транслитерация и kebab-case строго запрещены** — иначе вики-ссылки `[[...]]` в Obsidian не разрешатся.

### ФОРМАТ ВЫВОДА ДЛЯ НОВЫХ ФАЙЛОВ

```
---
folder: [Точное название папки из списка выше]
source_type: [тип источника: транскрипт | письмо | документ | заметки]
source: [название файла-источника из _inbox, без расширения]
created: [дата создания заметки, YYYYMMDD — дата текущего прогона]
modified: [дата последнего изменения, YYYYMMDD — при создании совпадает с created]
---

# [Суть описанной системы или процесса — краткий заголовок]

## 1. Текущее состояние (As-Is)
[Обобщённое описание того, как процесс или функция работает СЕЙЧАС, на структурном уровне. Фиксируй устройство процесса и системные проблемы, НЕ оперативные частности (конкретные числа по конкретным единицам, разовые случаи). Если что-то не формализовано или не работает — отметь это как факт настоящего.]

## 2. Ключевые роли и системы
* Каноничная Роль — зона ответственности
* Каноничная Система — функция

## 3. Правила и Взаимосвязи
* [Конкретное бизнес-правило/ограничение/зависимость — КАК именно устроено, при каком условии что происходит, какое требование действует. НЕ обобщённый вывод «проблема не решена» и не пересказ раздела 1: здесь фиксируются сами правила и связи, конкретикой.]
* Зависит от: [[Другая as-is заметка]]
* Влияет на: [[Другая as-is заметка]]
```

> **Раздел 3 — это правила, а не выводы.** Пиши конкретные ограничения и зависимости («чек на резервной кассе печатается без детализации позиций — несоответствие требованиям»), а не общие итоги («проблема критична и не решена»). Если по as-is есть только вывод без конкретного правила — перенеси фактуру из раздела 1 в виде правила, не схлопывай до лозунга.

> **Ссылки в шаблоне.** Имена ролей и систем в разделе 2 — обычным текстом, БЕЗ `[[]]` (у них нет своих заметок, ссылка была бы висячей; единообразие обеспечивает словарь). В разделе 3 `[[...]]` ставится ТОЛЬКО на ДРУГИЕ as-is заметки, которые реально существуют (создаются сейчас или найдены в папке) и только для важных связей; если связанной заметки нет — пиши сущность обычным текстом. Подробнее — Правило 3 агента `context-extractor`.

Файл описывает **текущее состояние** процесса, а не протокол совещания. Разделы для решений совещания и открытых вопросов в файл НЕ добавляются — это не часть As-Is контекста. Решения и открытые вопросы используются только для формирования пакета уточняющих вопросов пользователю.

### ЭТАЛОН ГЛУБИНЫ (нейтральный пример — образец ФОРМЫ и ГЛУБИНЫ, НЕ содержания)

Пример из абстрактного бизнес-домена. Он задаёт, насколько ПОДРОБНО раскрывать заметку. **Факты из него не копируй** — он другой темы; бери из него только уровень детализации. На него, а не на лаконичные заметки базы, равняй глубину.

**Так — НУЖНОЙ глубины (структурно, конкретно):**

```
# Согласование договоров с контрагентами

## 1. Текущее состояние (As-Is)
Договоры с новыми контрагентами согласуются последовательно через несколько подразделений: инициатор готовит проект, затем тот проходит юридическую проверку, финансовую оценку и подпись руководителя. Единой системы согласования нет — проекты передаются по почте и в мессенджерах, статус согласования централизованно нигде не фиксируется. Из-за этого инициатор узнаёт о застрявшем этапе только постфактум, а версии договора расходятся между участниками.

## 2. Ключевые роли и системы
* Инициатор договора — готовит проект и вручную ведёт его по этапам
* Юридическая проверка — согласует формулировки и правовые риски
* Финансовая оценка — проверяет условия оплаты и лимиты
* Почта и мессенджеры — фактический канал передачи проектов; выделенной системы согласования нет

## 3. Правила и Взаимосвязи
* На подпись договор уходит только после юридической И финансовой проверки — этапы идут последовательно, не параллельно
* Статус согласования нигде не фиксируется централизованно, поэтому застрявший этап выявляется лишь ручным опросом участников
* Единого источника актуальной версии нет: правки вносятся в разные копии, версии расходятся
```

**Так — НЕ надо (куце, смысл и правила схлопнуты в лозунги):**

```
# Согласование договоров

## 1. Текущее состояние (As-Is)
Договоры согласуются вручную через несколько отделов. Единой системы нет.

## 2. Ключевые роли и системы
* Инициатор
* Юрист
* Финансы

## 3. Правила и Взаимосвязи
* Процесс не автоматизирован
* Проблема не решена
```

Разница не в длине ради длины: в «хорошем» варианте видно КАК устроен процесс, у каждой роли — зона ответственности, а раздел 3 — конкретные правила и зависимости. В «плохом» — структура стёрта, роли без функций, правила выродились в лозунги. Целься в первый, даже если соседние заметки базы выглядят как второй.

> **Эталон задаёт ГЛУБИНУ одной заметки — НЕ её ширину и НЕ их число.** Это ОДНА атомарная as-is, раскрытая подробно. Глубина — НЕ повод делать меньше заметок: ты всё равно извлекаешь КАЖДУЮ самостоятельную as-is из перечня шага 3 отдельной УЗКОЙ заметкой (перечень шага 3 — пол по числу, глубина его не снижает). Глубокая заметка остаётся узкой — одна ситуация, а не сводка нескольких тем. Если ради глубины ты слил несколько as-is в одну заметку или сделал заметок меньше — это ошибка: глубина и охват/атомарность — независимые оси (см. «Обобщение, а не стенограмма» агента). Сначала зафиксируй ВСЕ атомарные as-is (число — как на пустой базе), потом каждую раскрой на эту глубину. **Эталон — ПОТОЛОК глубины, а не минимальный порог «достаточной фактуры»:** тонкая as-is получает короткую заметку, а НЕ исключение. «Недостаточно содержания для глубокой заметки» — не повод не делать заметку; глубина эталона задаёт, как раскрывать, а не что́ заслуживает быть заметкой.
